# ドキュメントの書き方

ADR・設計ガイド・rules・AGENTS.md を書くときの手順と、その形にしている理由を持つ。

| 決定                                                                                                                                              | ADR      |
| ------------------------------------------------------------------------------------------------------------------------------------------------- | -------- |
| 決定は 1 本に 1 つずつ ADR に記録し、枠内の調整は書き換え、決定が変わったら新しい ADR で置き換える                                                | ADR-0000 |
| ドキュメントは規範・設計ガイド・決定・docstring・履歴の層に分け、ADR は構造・品質特性・戻しにくさに効く選択に限り、参照は規範の側から一方向に張る | ADR-0001 |
| rules は見出しと箇条書きで 1 項目 1 規範に分け、消したら誤る規範だけを書き、lint が止めるものは書かない                                           | ADR-0002 |

## how-to

### ADR を書く

メタデータの書き方と一覧への追記は `docs/decisions/README.md`「新しい ADR を書く手順」に従う。節は最低限次の 3 つにし、題材に応じて足す。

| 節           | 書くもの                                                                           |
| ------------ | ---------------------------------------------------------------------------------- |
| Context      | 背景・制約・要件。判断の前提                                                       |
| Decision     | 何を選んだか。検討した選択肢の比較表 (候補 / 評価軸 / 採否) と却下理由を必ず含める |
| Consequences | 採用した結果として起きること (良い面、悪い面、再評価の条件)                        |
| 任意         | 「調査結果」(実測の根拠)、「設定上の注意 / リスク」、「出典」                      |

本文は次のように書く。

- 主張は実コードと実測で裏づける。コードは `src/path/to/file.ts` のようにファイルパスで指す
- 決定の文を個別の部品名に依存させない。部品は改名されるが ADR は改名に追随しないので、決定が宙に浮く。根拠としてファイルパスを挙げるのはよい
- 外部の料金やライブラリの仕様のように変わる数値は、前提と確認した日を添え、出典の URL を「出典」節に置く
- 手順や規範の表が育ってきたら、ADR に置かずこのディレクトリのガイドへ出す (ADR-0001)

### ADR を変えたら参照している側を直す

ADR を書き換えたとき、`Superseded` や `Deprecated` にしたとき、分けたときは、`git grep -n 'ADR-NNNN'` でその ADR を出典にしている rules・ガイド・コードのコメント・AGENTS.md・README を洗い、中身に合わせて直す。
`scripts/checks/integrity/adr-index.test.ts` は ADR ファイルと索引の対応だけを見て、本文の `ADR-NNNN` の行き先は見ない (ADR-0000)。行き先の無い番号や、分けたあとに別の決定を指している番号は、この grep でしか見つからない。

### 1 つの文書の中で書かないもの

| 書かないもの                    | 代わりに書くもの                   | 理由                                                                                 |
| ------------------------------- | ---------------------------------- | ------------------------------------------------------------------------------------ |
| チャット内の参照 (`[Image #N]`) | 画像が示していた中身を文章で       | 会話が消えると参照先が無くなる                                                       |
| 指示語 (「本 PR」「今回の」)    | PR 番号、日付、commit hash         | 書いた時点の文脈を知らない読み手には、どの PR か分からない                           |
| 相対日付 (「昨日」「先週」)     | `YYYY-MM-DD`                       | 読む日によって指す日が変わる                                                         |
| 既存の項目と重なる追記          | 既存の項目への統合、古い項目の削除 | 追記だけを重ねると、同じ主題の項目が離れた場所に並び、どれが現在の規範か読めなくなる |

### rules の項目を書く

- 手順、選択肢の順序、具体的な組み立て方、打ち消せない落とし穴、適用範囲の確定は、どれも理由ではなく規範である。1 行の規範として rules に残し、手順の詳しい組み方と理由だけをガイドへ出す。規範ごと移すと、作業中に読み込まれる rules から規範が消える (ADR-0003)
- 対象の種別で対応が決まる規範 (「A のときは X、B のときは Y」) は表で書く。箇条書きより引きやすい
- 同じ主題の規範を離れた項目に分散させない

### AGENTS.md を書く

- コミットの書式やブランチの運用のような運用規約は、テンプレート由来のものを置かず、利用する側が自分のものを足す
- AGENTS.md の行数の上限は手書きの行だけで数え、ツールが書き戻すマーカー区間 (`<!--VITE PLUS START-->` 〜 `END` など) は数えない。区間の中身はツールが次の更新で書き戻すので削れず、数えると守れない上限になる

### ガイドを書く

| 対象               | 書き方                                                                                                                            |
| ------------------ | --------------------------------------------------------------------------------------------------------------------------------- |
| 主題               | 1 本に 1 主題。ファイル名は主題の英語名を小文字と dash にしたもの (`lists-and-search.md`)。一覧は `docs/guides/README.md`         |
| 節                 | 見出しの下で how-to (手順と落とし穴への対処) と explanation (なぜその形か) を分け、1 つの節に手順と理由を混ぜない                 |
| 冒頭               | 主題に関わる ADR を、題をそのまま写した表で並べる。決定を言い換えない                                                             |
| コード             | ファイルパスで指す。コードを貼らず、行番号を書かない。行番号は編集でずれ、ずれても気付けない                                      |
| ADR                | 決定を言い換えず `ADR-NNNN` で指す。ガイドが持つのは、決定に沿って組む手順と、決定の前提になる仕組みの説明                        |
| 経緯               | 書かない。以前の手順と変えた理由は git 履歴が持つ。コードと決定が変わったら、その場で書き換える                                   |
| 数値               | ADR-0001「数値の階層」に従う。上流の挙動の観測には日付と版を添える                                                                |
| ADR から移した作法 | 作法の選び方で比較した案と却下の理由は explanation に残す (決定の比較は ADR に残す)。判断の根拠を兼ねる日付つきの数値は落とさない |

- ガイドの手順が指すファイルを rename したら、`git grep -n '<旧パス>' docs/guides` で直す。パスの参照は機械で検査しない
- 1 本が長くなり主題が 2 つ混ざったら、ファイルを分けて `docs/guides/README.md` の一覧を直す

### 文書に書いた比を数え直す

コントラスト比は書き写さず、`mise run contrast` で測る (`docs/guides/styling-and-tokens.md`「残す数値と落とす数値」)。文書とソースに比が残っていないかは次で洗う。

```bash
grep -rnE '\b[0-9]{1,2}\.[0-9]{2}\b|[0-9]+(\.[0-9]+)?\s*[:対]\s*1\b' \
  --include='*.md' --include='*.ts' --include='*.tsx' --include='*.css' \
  docs/ src/ scripts/ .claude/
```

- 比は `4.5:1` とも `4.21` とも書かれるので、`:1` を要求すると後者を取りこぼす。代わりに 2 桁の小数も拾うので、`oklch()` の成分 (`oklch(0.97 0.014 254.604)`) が混ざる。出た行は読んで分ける
- `src/styles.css` の比は宣言と同じ行のコメントに載る (`--primary: oklch(42.4% …); /* … 4.21 */`)。`oklch()` の成分と同居するので、ノイズとして飛ばさず 1 行ずつ読む
- 出た数値を残すか落とすかは、`docs/guides/styling-and-tokens.md`「残す数値と落とす数値」の種別 (再計算できるか) で決める

## explanation

### ガイドの書き方を選んだ理由

書き方を決めずにガイドを書くと、次のことが揃わない。

| 揃わないもの         | 壊れ方                                                                                         |
| -------------------- | ---------------------------------------------------------------------------------------------- |
| 1 本に入れる主題     | 手順を探す人が、どのファイルを開けばよいか決められない                                         |
| 手順と説明の混ざり方 | 手順だけを追いたい人が理由の段落を読み飛ばせない。理由を知りたい人は手順の中から拾うことになる |
| コードの載せ方       | 抜き書きしたコードが実装と食い違っても、ガイド側では気付けない                                 |
| ADR との関係         | 決定をガイドで言い換えると、ADR を改訂したときにガイドだけが古い決定を言い続ける               |
| 改訂の扱い           | 書き換えず、変えたら新しい版を足していくと決めると、古い手順が現在の手順と並ぶ                 |

参考にした枠組みと先行例は次のとおり。

| 出典          | 中身                                                                                                                                                                                                                                                                                                          |
| ------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Diátaxis      | 文書を 4 種に分ける。how-to guide は "directions that guide the reader through a problem or towards a result. How-to guides are goal-oriented."、explanation は "a discursive treatment of a subject, that permits reflection. Explanation is understanding-oriented." (https://diataxis.fr/)                 |
| arc42 Tip 8-4 | "Explain, how these concepts are applied in reality, how they are implemented in source code. You can refer to existing code, or include code examples in the documentation." (https://docs.arc42.org/tips/8-4/)                                                                                              |
| arc42 Tip 8-8 | コード片をコピーして文書に貼らない。自動で取り込めないなら、場所でコードを指す (https://docs.arc42.org/tips/8-8/)                                                                                                                                                                                             |
| Catio         | "Design documents are kept up to date as the system evolves; ADRs are immutable once accepted and are superseded by new ADRs rather than edited." 引くのは設計文書の側だけで、このリポジトリの ADR の扱いは ADR-0000 が決める (枠内なら書き換える) (https://www.catio.tech/blog/architecture-decision-record) |

Tip 8-4 はコードを文書に載せることも認めるが、ここでは貼らずに場所で指す。貼る形を採らない根拠は Tip 8-8 である。

| 案                                                           | 評価                                                                                                         | 採否     |
| ------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------ | -------- |
| 1 本 1 主題、中を how-to と explanation の節に分ける         | 同じ主題の手順と理由が 1 ファイルに並び、節で読み分けられる                                                  | **採用** |
| Diátaxis に合わせて how-to と explanation を別ファイルにする | 同じ作法の手順と理由が別ファイルに離れ、片方だけが直される。主題の数だけファイルが倍になる                   | 却下     |
| コードを抜き書きして載せる                                   | 読み手は開かずに済むが、実装が変わっても抜き書きは変わらない (Tip 8-8)                                       | 却下     |
| ADR の決定を要約して載せる                                   | ガイドだけで読めるが、ADR を改訂すると要約が古い決定を言い続ける                                             | 却下     |
| 書き換えず、変えたら新しい版を足す                           | 古い手順が現在の手順と並び、どれに従うかを読み手が判別する必要がある。Catio は設計文書を更新し続ける側に置く | 却下     |
