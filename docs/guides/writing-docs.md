# ドキュメントの書き方

ADR・設計ガイド・rules・AGENTS.md を書くときの手順と、その形にしている理由を持つ。

| 決定                                                                                                                                                   | ADR      |
| ------------------------------------------------------------------------------------------------------------------------------------------------------ | -------- |
| 決定は 1 本に 1 つずつ ADR に記録し、枠内の調整は書き換え、決定が変わったら新しい ADR で置き換える                                                     | ADR-0000 |
| ドキュメントは rules・設計ガイド・決定・docstring・履歴の層に分け、ADR は構造・品質特性・戻しにくさに効く選択に限り、参照は rules の側から一方向に張る | ADR-0001 |
| rules は見出しと箇条書きで 1 項目 1 規範に分け、消したら誤る規範だけを書き、lint が止めるものは書かない                                                | ADR-0002 |
| 規範の置き場所は読み込まれる契機で決め、Bash で打つだけの操作の規範の写しは AGENTS.md に置き、rules は設計ガイドを import せず読むようにも書かない     | ADR-0003 |

## how-to

### ADR を書く

メタデータの書き方と一覧への追記は `docs/decisions/README.md`「新しい ADR を書く手順」に従う。節は最低限次の 3 つにし、題材に応じて足す。

| 節           | 書くもの                                                                           |
| ------------ | ---------------------------------------------------------------------------------- |
| Context      | 背景・制約・要件。判断の前提                                                       |
| Decision     | 何を選んだか。検討した選択肢の比較表 (候補 / 評価軸 / 採否) と却下理由を必ず含める |
| Consequences | 採用した結果として起きること (良い面、悪い面、再評価の条件)                        |
| 任意         | 「調査結果」(実測の根拠)、「設定上の注意 / リスク」、「出典」                      |

本文は次のように書く。

- 主張は実コードと実測で裏づける。コードは `src/path/to/file.ts` のようにファイルパスで指す
- 決定の文を個別の部品名に依存させない。部品は改名されるが ADR は改名に追随しないので、決定が宙に浮く。根拠としてファイルパスを挙げるのはよい
- 外部の料金やライブラリの仕様のように変わる数値は、前提と確認した日を添え、出典の URL を「出典」節に置く
- 決定から派生した手順や規範の表が育ってきたら、ADR に置かずこのディレクトリのガイドへ出す (ADR-0001)

### ADR を変えたら参照している側を直す

ADR を書き換えたとき、`Superseded` や `Deprecated` にしたとき、分けたときは、`git grep -n 'ADR-NNNN'` でその ADR を出典にしている rules・ガイド・コードのコメント・AGENTS.md・README を洗い、中身に合わせて直す。
`scripts/checks/integrity/adr-index.test.ts` は ADR ファイルと索引の対応だけを見て、本文の `ADR-NNNN` の行き先は見ない (ADR-0000)。行き先の無い番号や、分けたあとに別の決定を指している番号は、この grep でしか見つからない。

### 1 つの文書の中で書かないもの

| 書かないもの                    | 代わりに書くもの                   | 理由                                                                                 |
| ------------------------------- | ---------------------------------- | ------------------------------------------------------------------------------------ |
| チャット内の参照 (`[Image #N]`) | 画像が示していた中身を文章で       | 会話が消えると参照先が無くなる                                                       |
| 指示語 (「本 PR」「今回の」)    | PR 番号、日付、commit hash         | 書いた時点の文脈を知らない読み手には、どの PR か分からない                           |
| 相対日付 (「昨日」「先週」)     | `YYYY-MM-DD`                       | 読む日によって指す日が変わる                                                         |
| 既存の項目と重なる追記          | 既存の項目への統合、古い項目の削除 | 追記だけを重ねると、同じ主題の項目が離れた場所に並び、どれが現在の規範か読めなくなる |

### rules の項目を書く

- 手順、選択肢の順序、具体的な組み立て方、打ち消せない落とし穴、適用範囲の確定は、どれも理由ではなく規範である。規範の本体をガイドの how-to (ADR の決定そのものなら ADR) に書き、rules には規範 1 行に畳んで写し、規範から読み取れない事情があれば理由 1 文を添える (ADR-0002)。rules に無いと作業中に読み込まれず (ADR-0003)、本体に無いと Claude を介さない開発に届かない (ADR-0001)
- 手順の詳しい組み方と、理由 1 文を超える説明は rules に書かず、本体に置く (ADR-0002)
- ライブラリが関わる規範は、本体に公式の該当箇所を引く。公式から外れる書き方と、公式の複数の手段から 1 つを選ぶ書き方は、本体に理由を書く (ADR-0001)
- 本体と写しが食い違ったら本体を正とする。規範を変えるときは本体を先に直し、写しを追随させる (ADR-0001)
- Claude Code のツール・skill・MCP の使い方だけを決める規範は、rules か AGENTS.md にだけ置き、上流の docs を出典にしてよい。人の開発にも効く規約は含めない (ADR-0001)
- 対象の種別で対応が決まる規範 (「A のときは X、B のときは Y」) は表で書く。箇条書きより引きやすい
- 同じ主題の規範を離れた項目に分散させない

### AGENTS.md を書く

- AGENTS.md に書く規範は、rules と同じく本体 (ガイドか ADR) の写しにする。Claude Code のツール・skill・MCP の使い方だけを決める規範は除く (ADR-0001)
- `CLAUDE.md` は `AGENTS.md` への symlink なので、編集は `AGENTS.md` に対して行う
- 手書きの行は 50 行以下を目標、100 行を上限にする。超えそうなら、ファイルを読む場面の規範を `paths` 付きの rules へ分け、Bash で打つだけの操作の規範の写しは AGENTS.md に残す。AGENTS.md は毎セッション全文が読み込まれる (ADR-0003)
- コミットの書式やブランチの運用のような運用規約は、テンプレート由来のものを置かず、利用する側が自分のものを足す
- AGENTS.md の行数の上限は手書きの行だけで数え、ツールが書き戻すマーカー区間 (`<!--VITE PLUS START-->` 〜 `END` など) は数えない。区間の中身はツールが次の更新で書き戻すので削れず、数えると守れない上限になる

### ほかの文書を指す

| 規範                                                                                                               | 理由                                                     |
| ------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------- |
| リポジトリ内のほかの文書の文言を引用せず、番号や見出しで指す。外部の出典 (ライブラリの公式など) は原文で引いてよい | 引用元が書き換わると、引用が宙に浮く                     |
| ADR は `ADR-NNNN` で指す                                                                                           | スラッグが変わっても番号は変わらないので、参照が保たれる |
| ADR への markdown リンクは `docs/decisions/README.md` の一覧と `Superseded-by` の補助リンクだけに張る              | リンクはファイル名を持つので、改名で切れる               |
| 項目を序数 (「例外 4」) で指さない                                                                                 | 序数は編集でずれ、ずれても静かに壊れる                   |
| rules の見出し語を変えたら、`grep -rn "<旧見出し語>" .claude/rules/ AGENTS.md` で指している側を直す                | 見出し語への参照は機械で検査しない                       |
| 決定を別の文書へ移すときは、移した先が覆した内容を自分の言葉で持つ                                                 | 旧側を書き換えるだけでは、根拠が git 履歴にしか残らない  |
| 陳腐化したポインタは、注記を足さず文ごと削除する                                                                   | 注記を重ねると、どれが現在の参照か読めなくなる           |

### 作業の文書を扱う

- `docs/superpowers/` の spec と plan は作業のための文書で、作業が終わったら書き換えない。決定は ADR、規範はガイドに書く。作業の文書を書き換えると、当時の判断の記録が失われる

### 書くか削るかを決める

- 1 文ずつ「これを消したら、読み手が誤った選択をするか」を問い、しないなら削る。[Claude Code docs「Best practices」][] が CLAUDE.md について書く "For each line, ask: _\"Would removing this cause Claude to make mistakes?\"_ If not, cut it." を、文書全般に当てる

### ガイドを書く

| 対象                     | 書き方                                                                                                                                                                                             | 理由                                                                                                                                                                                                                                 |
| ------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 主題                     | 1 本に 1 主題を置く。2 つ目の主題が混ざったら、別のファイルに分ける                                                                                                                                | 主題が混ざると、手順を探す人がどのファイルを開けばよいか決められない                                                                                                                                                                 |
| ファイル名               | 主題の英語名を小文字と dash にする (`lists-and-search.md`)                                                                                                                                         | 大文字小文字だけが違う名前は、大文字小文字を区別しないファイルシステムで同じファイルとみなされ ([git-config「core.ignoreCase」][])、ASCII 以外の文字は macOS が分解した形で名前に残りうる ([git-config「core.precomposeUnicode」][]) |
| 小主題                   | 1 つの主題の中で小主題が増えたら、主題名のディレクトリを作り、小主題ごとに 1 本ずつ置く (`testing/waiting-and-assertions.md`)                                                                      | 接頭辞で並べると (`testing-waiting.md`)、一覧が長くなり、主題のまとまりがファイル名にしか現れない                                                                                                                                    |
| how-to と explanation    | 一覧の `docs/guides/README.md` を除くどのファイルにも、`## how-to` と `## explanation` を両方置く。2 つを別のファイルに分けない                                                                    | 別のファイルに分けると、同じ作法の手順と理由が離れ、片方だけが直される                                                                                                                                                               |
| 一覧                     | ガイドを足す・分ける・改名したら、`docs/guides/README.md` の一覧を直す                                                                                                                             | 一覧に無いガイドは、一覧から主題を探す人に見つからない                                                                                                                                                                               |
| how-to の節              | 規範、手順、落とし穴への対処と、規範から読み取れない事情があればその理由を書く。その形を選んだ理由 (案の比較、出典の解説) は explanation に書く                                                    | 選んだ理由を how-to に混ぜると、手順だけを追う人が理由の段落を読み飛ばせない ([Diátaxis「How-to guides」][])                                                                                                                         |
| 冒頭の表                 | 主題に関わる ADR を、冒頭に「決定 / ADR」の表で並べる。関わる ADR が無いガイドには表を置かない                                                                                                     | 表が無いと、ガイドの手順がどの決定に沿っているかを本文から探すことになる                                                                                                                                                             |
| 冒頭の表の題             | 決定の列には、ADR の 1 行目の `ADR-NNNN: ` の後ろの題をそのまま写す                                                                                                                                | そのまま写した題は ADR の 1 行目と文字列で突き合わせられ、言い換えた題は ADR と別の決定を述べていても気付けない                                                                                                                      |
| コード                   | このリポジトリの実装はファイルパスで指し、抜き書きして貼らない。組み方を示す短い例 (`…` で省いた骨組みや、最小のテスト) と、測り方のコマンドやスクリプトは書いてよい                               | 抜き書きは実装が変わっても変わらず、食い違ってもガイドの側では気付けない ([arc42 Tip 8-8][])                                                                                                                                         |
| 行番号                   | このリポジトリのファイルの行番号を書かない。上流のコードは commit SHA に固定した permalink で指してよい                                                                                            | 行番号は編集でずれ、ずれても気付けない                                                                                                                                                                                               |
| ADR                      | ADR の決定は言い換えず `ADR-NNNN` で指す。ADR に関わる内容としてガイドが書くのは、決定に沿って組む手順と、決定の前提になる仕組みの説明にする                                                       | 決定を要約すると、ADR を書き換えたときに要約が古い決定を言い続ける                                                                                                                                                                   |
| 経緯                     | 以前の手順と変えた理由は書かず、コードと決定が変わったらその場で書き換える。経緯は git 履歴が持つ                                                                                                  | 書き換えずに新しい版を足すと、古い手順が現在の手順と並び、どれに従うかを読み手が判別することになる ([Catio][])                                                                                                                       |
| 出典                     | 本文は出典を名前の参照リンク (`[Vitest docs「Test Annotations」][]`) で挙げ、URL を書かない。URL はファイル末尾の `## 出典` のリンクの定義 (`[名前]: URL`) に置く                                  | 本文に URL を書くと、言及のたびに URL が重なって項目が長くなり、URL を変えるときに全ての言及を直すことになる                                                                                                                         |
| 出典の言及               | 同じ出典に言及するたびにリンクにする                                                                                                                                                               | 最初の言及だけをリンクにすると、後の節だけを開いた読み手は出典を開けない                                                                                                                                                             |
| 出典の名前               | リンクの文字列を定義の名前に一致させる (照合では大文字小文字と空白の違いだけが無視される)。`gh api markdown -f mode=gfm -f text="$(cat <file>)"` の出力で、コードの外に `][]` が残らないことを見る | 一致しないと定義に当たらず、リンクにならないまま括弧で表示される ([CommonMark の仕様][] 6.3「Links」)                                                                                                                                |
| 出典の節の導入           | `## 出典` の直下に、本文の出典の名前がリンクになっていることと、名前と URL の対応がリンクの定義にあることを書く。固定した版や観測した日があれば、その後ろに続ける                                  | リンクの定義は描画される要素にならないので ([CommonMark の仕様][] 4.7「Link reference definitions」)、導入が無いと描画した画面に見出しだけが残る                                                                                     |
| 読んだだけの出典         | 本文から引かずに読んだ出典は、`## 出典` の中で補足つきの参照リンクの一覧にする                                                                                                                     | リンクの定義だけを置くと描画されず、何のために読んだかも残らない                                                                                                                                                                     |
| ADR から移した作法の比較 | ADR からガイドへ作法を移したら、作法の選び方で比較した案と却下の理由を explanation に残す。決定そのものの比較は ADR に残す                                                                         | 落とすと、移した作法がなぜその形かをどの文書からも辿れなくなる                                                                                                                                                                       |
| パスの参照               | ガイドの手順が指すファイルを rename したら、`git grep -n '<旧パス>' docs/guides` で直す                                                                                                            | パスの参照は機械で検査しないので、古いパスが残っても気付けない                                                                                                                                                                       |

### 文書に書いた比を数え直す

コントラスト比は書き写さず、`mise run contrast` で測る (`docs/guides/styling-and-tokens.md`「残す数値と落とす数値」)。文書とソースに比が残っていないかは次で洗う。

```bash
grep -rnE '\b[0-9]{1,2}\.[0-9]{2}\b|[0-9]+(\.[0-9]+)?\s*[:対]\s*1\b' \
  --include='*.md' --include='*.ts' --include='*.tsx' --include='*.css' \
  docs/ src/ scripts/ .claude/
```

- 比は `4.5:1` とも `4.21` とも書かれるので、`:1` を要求すると後者を取りこぼす。代わりに 2 桁の小数も拾うので、`oklch()` の成分 (`oklch(0.97 0.014 254.604)`) が混ざる。出た行は読んで分ける
- `src/styles.css` の比は宣言と同じ行のコメントに載る (`--primary: oklch(42.4% …); /* … 4.21 */`)。`oklch()` の成分と同居するので、ノイズとして飛ばさず 1 行ずつ読む
- 出た数値を残すか落とすかは、`docs/guides/styling-and-tokens.md`「残す数値と落とす数値」の種別 (再計算できるか) で決める

## explanation

### ガイドの書き方を選んだ理由

書き方を決めずにガイドを書くと、次のことが揃わない。

| 揃わないもの         | 壊れ方                                                                                         |
| -------------------- | ---------------------------------------------------------------------------------------------- |
| 1 本に入れる主題     | 手順を探す人が、どのファイルを開けばよいか決められない                                         |
| 手順と説明の混ざり方 | 手順だけを追いたい人が理由の段落を読み飛ばせない。理由を知りたい人は手順の中から拾うことになる |
| コードの載せ方       | 抜き書きしたコードが実装と食い違っても、ガイド側では気付けない                                 |
| ADR との関係         | 決定をガイドで言い換えると、ADR を改訂したときにガイドだけが古い決定を言い続ける               |
| 改訂の扱い           | 書き換えず、変えたら新しい版を足していくと決めると、古い手順が現在の手順と並ぶ                 |

参考にした枠組みと先行例は次のとおり。

| 出典              | 中身                                                                                                                                                                                                                                                                                                                                 |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| [Diátaxis][]      | 文書を 4 種に分ける。how-to guide は "directions that guide the reader through a problem or towards a result. How-to guides are goal-oriented." ([Diátaxis「How-to guides」][])、explanation は "a discursive treatment of a subject, that permits reflection. Explanation is understanding-oriented." ([Diátaxis「Explanation」][]) |
| [arc42 Tip 8-4][] | "Explain, how these concepts are applied in reality, how they are implemented in source code. You can refer to existing code, or include code examples in the documentation."                                                                                                                                                        |
| [arc42 Tip 8-8][] | コード片をコピーして文書に貼らない。自動で取り込めないなら、場所でコードを指す                                                                                                                                                                                                                                                       |
| [Catio][]         | "Design documents are kept up to date as the system evolves; ADRs are immutable once accepted and are superseded by new ADRs rather than edited." 引くのは設計文書の側だけで、このリポジトリの ADR の扱いは ADR-0000 が決める (枠内なら書き換える)                                                                                   |

[arc42 Tip 8-4][] はコードの例を文書に載せることも認めるが、このリポジトリの実装は貼らずに場所で指す。実装を貼る形を採らない根拠は [arc42 Tip 8-8][] である。

| 案                                                                              | 評価                                                                                                                                                                                                                                                                                                                                                                                                                                     | 採否     |
| ------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------- |
| 1 本 1 主題、中を how-to と explanation の節に分ける                            | 同じ主題の手順と理由が 1 ファイルに並び、節で読み分けられる                                                                                                                                                                                                                                                                                                                                                                              | **採用** |
| 主題が大きくなったら同名のディレクトリに分け、中を小主題ごとに 1 本にする       | 主題のまとまりがディレクトリで見え、小主題のファイルの中で手順と理由が並ぶ                                                                                                                                                                                                                                                                                                                                                               | **採用** |
| how-to に、規範から読み取れない事情を理由として書く                             | [Diátaxis「How-to guides」][] は how-to を "action and only action" とし、説明は "if they're important, link to them" とするので、そこから外れる。外れるのは、rules と AGENTS.md の写しがそうした事情を理由 1 文で持ち (ADR-0002)、本体の how-to に理由が無いと写しにしか理由が残らないため                                                                                                                                              | **採用** |
| how-to には規範と手順だけを書き、理由はすべて explanation に置く                | [Diátaxis「How-to guides」][] のとおりだが、how-to の規範を写した rules の項目の理由が、本体の how-to のどの行にも無くなる                                                                                                                                                                                                                                                                                                               | 却下     |
