# ドキュメントの書き方

ADR・設計ガイド・rules・AGENTS.md を書くときの手順と、その形にしている理由を持つ。

| 決定                                                                                                                          | ADR      |
| ----------------------------------------------------------------------------------------------------------------------------- | -------- |
| 決定は 1 本に 1 つずつ ADR に記録し、枠内の調整は書き換え、決定が変わったら新しい ADR で置き換える                            | ADR-0000 |
| ドキュメントを規範・設計ガイド・決定・履歴の層に分け、参照は規範の側から一方向に張る                                          | ADR-0001 |
| rules は見出しと箇条書きで 1 項目 1 規範に分け、消したら誤る規範だけを書き、lint が止めるものは書かない                       | ADR-0002 |
| ADR にするのは構造・主要な品質特性・戻しにくさに効く選択に限り、部品をまたぐ作法はガイド、部品に閉じた注意は docstring に置く | ADR-0007 |
| 設計ガイドは 1 本に 1 主題を持ち、手順と説明を節で分け、コードと決定は参照で指す                                              | ADR-0006 |

## how-to

### ADR を書く

メタデータの書き方と一覧への追記は `docs/decisions/README.md`「新しい ADR を書く手順」に従う。節は最低限次の 3 つにし、題材に応じて足す。

| 節           | 書くもの                                                                           |
| ------------ | ---------------------------------------------------------------------------------- |
| Context      | 背景・制約・要件。判断の前提                                                       |
| Decision     | 何を選んだか。検討した選択肢の比較表 (候補 / 評価軸 / 採否) と却下理由を必ず含める |
| Consequences | 採用した結果として起きること (良い面、悪い面、再評価の条件)                        |
| 任意         | 「調査結果」(実測の根拠)、「設定上の注意 / リスク」、「出典」                      |

本文は次のように書く。

- 主張は実コードと実測で裏づける。コードは `src/path/to/file.ts` のようにファイルパスで指す
- 決定の文を個別の部品名に依存させない。部品は改名されるが ADR は改名に追随しないので、決定が宙に浮く。根拠としてファイルパスを挙げるのはよい
- 外部の料金やライブラリの仕様のように変わる数値は、前提と確認した日を添え、出典の URL を「出典」節に置く
- 手順や規範の表が育ってきたら、ADR に置かずこのディレクトリのガイドへ出す (ADR-0007)

### ADR を変えたら参照している側を直す

ADR を書き換えたとき、`Superseded` や `Deprecated` にしたとき、分けたときは、`git grep -n 'ADR-NNNN'` でその ADR を出典にしている rules・ガイド・コードのコメント・AGENTS.md・README を洗い、中身に合わせて直す。
`scripts/checks/integrity/adr-index.test.ts` は ADR ファイルと索引の対応だけを見て、本文の `ADR-NNNN` の行き先は見ない (ADR-0000)。行き先の無い番号や、分けたあとに別の決定を指している番号は、この grep でしか見つからない。

### 1 つの文書の中で書かないもの

| 書かないもの                    | 代わりに書くもの                   | 理由                                                                                 |
| ------------------------------- | ---------------------------------- | ------------------------------------------------------------------------------------ |
| チャット内の参照 (`[Image #N]`) | 画像が示していた中身を文章で       | 会話が消えると参照先が無くなる                                                       |
| 指示語 (「本 PR」「今回の」)    | PR 番号、日付、commit hash         | 書いた時点の文脈を知らない読み手には、どの PR か分からない                           |
| 相対日付 (「昨日」「先週」)     | `YYYY-MM-DD`                       | 読む日によって指す日が変わる                                                         |
| 既存の項目と重なる追記          | 既存の項目への統合、古い項目の削除 | 追記だけを重ねると、同じ主題の項目が離れた場所に並び、どれが現在の規範か読めなくなる |

### rules の項目を書く

- 手順、選択肢の順序、具体的な組み立て方、打ち消せない落とし穴、適用範囲の確定は、どれも理由ではなく規範である。1 行の規範として rules に残し、手順の詳しい組み方と理由だけをガイドへ出す。規範ごと移すと、作業中に読み込まれる rules から規範が消える (ADR-0005)
- 対象の種別で対応が決まる規範 (「A のときは X、B のときは Y」) は表で書く。箇条書きより引きやすい
- 同じ主題の規範を離れた項目に分散させない

### AGENTS.md を書く

- コミットの書式やブランチの運用のような運用規約は、テンプレート由来のものを置かず、利用する側が自分のものを足す
- AGENTS.md の行数の上限は手書きの行だけで数え、ツールが書き戻すマーカー区間 (`<!--VITE PLUS START-->` 〜 `END` など) は数えない。区間の中身はツールが次の更新で書き戻すので削れず、数えると守れない上限になる

### 文書に書いた比を数え直す

コントラスト比は書き写さず、`mise run contrast` で測る (ADR-0037)。文書とソースに比が残っていないかは次で洗う。

```bash
grep -rnE '\b[0-9]{1,2}\.[0-9]{2}\b|[0-9]+(\.[0-9]+)?\s*[:対]\s*1\b' \
  --include='*.md' --include='*.ts' --include='*.tsx' --include='*.css' \
  docs/ src/ scripts/ .claude/
```

- 比は `4.5:1` とも `4.21` とも書かれるので、`:1` を要求すると後者を取りこぼす。代わりに 2 桁の小数も拾うので、`oklch()` の成分 (`oklch(0.97 0.014 254.604)`) が混ざる。出た行は読んで分ける
- `src/styles.css` の比は宣言と同じ行のコメントに載る (`--primary: oklch(42.4% …); /* … 4.21 */`)。`oklch()` の成分と同居するので、ノイズとして飛ばさず 1 行ずつ読む
- 出た数値を残すか落とすかは、ADR-0037 の種別 (再計算できるか) で決める
