# ADR-0032: テストの import を重くする依存のバレルは使わず、個別エントリポイントから引き、lint で止める

- Status: Accepted
- Date: 2026-10-07
- 関連: ADR-0008 (同じ `no-restricted-imports` の override を持つ)、ADR-0031 (暦の日付と Calendar の扱い)

## Context

依存が関数やロケールをまとめて再 export する入口 (バレル) から 1 つを import すると、使わない周辺のモジュールまで読み込まれる。テストはファイルごとに import をやり直すので、その時間がテストの実行時間に積み上がる。Vitest docs「Profiling Test Performance」は、テストの import が遅いときの手段として "Use Specific Entry Points"、"Use `resolve.alias` to Redirect Imports"、"Use the Dependency Optimizer" の 3 つを挙げ、最初の例に `date-fns` → `date-fns/format` を使う。

テンプレートの依存で最初に当たるのは date-fns である。2026-09-27 に date-fns 4.4.0 で数えると、`index.js` は 245 行、`locale.js` は 95 行の `export * from` を持つ。テンプレートで probe を 1 つずつ実行し、テストファイルの import の時間 (`collectDuration`) と `--experimental.importDurations.print` の内訳を測った (「調査結果」)。unit project と browser project の両方で、バレルと個別エントリポイントの差が回ごとのばらつきを超えた。

lint が止めるのはアプリのコードが書く specifier で、依存の中の import には届かない。2026-10-07 に react-day-picker 10.0.2 の `dist/esm` を読むと、内部は date-fns を関数ごとの個別エントリポイントから import する (`dist/esm/classes/DateLib.js`) ので、Calendar を描く経路に date-fns のバレルは無い。アプリのコードが書く specifier では、`react-day-picker/locale/ja` が `date-fns/locale/ja` を import し (`dist/esm/locale/ja.js` の 1 行目)、`react-day-picker/locale` が `date-fns/locale` のバレルを再 export する (`dist/esm/locale.js` の 1 行目)。

## Decision

- 依存を import するときは、個別エントリポイントがあればそちらから引き、バレルを使わない
- 実測でバレルがテストの import を重くする依存を、`tooling/lint/config.ts` の `RESTRICTED_BARREL_IMPORTS` に名指しで足し、`no-restricted-imports` の `paths` で止める。メッセージで個別エントリポイントを案内する。足す手順は `docs/guides/dependencies-and-toolchain.md`「依存をバレルの禁止の対象に足す」にある
- 最初の対象は date-fns の `date-fns` と `date-fns/locale` である
- `RESTRICTED_BARREL_IMPORTS` はトップレベルの `rules` と、テスト専用コードの import 禁止の override (ADR-0008) の両方へ渡す。override は同じルールのオプションを置き換える (「調査結果」)
- 型だけの import も止まる (`allowTypeImports` の既定は `false`)。型が要るときは、依存先の型 (react-day-picker の `DayPickerLocale`) か関数の引数の型から取る

## Consequences

- 依存を足すか使い始めたときに、バレルしか使っていなければ測って判断する手間が増える。測り方はガイドにある
- `paths` は specifier の完全一致なので、`date-fns/locale` のバレルを再 export する `react-day-picker/locale` は止まらない。Calendar の locale は `react-day-picker/locale/<locale>` から引く
- `RESTRICTED_BARREL_IMPORTS` をトップレベルか override の片方からだけ外すと、外した側の範囲で無言で効かなくなる。`scripts/checks/integrity/lint-config.test.ts` はルールのオプションの中身を見ないので、この外し方を捕まえない (「調査結果」の、トップレベルだけに `paths` を置いた設定)
- 残った課題: 同じ測り方で測る候補は、lucide-react など、テンプレートのコードがルートから import している依存。測って重ければ `RESTRICTED_BARREL_IMPORTS` に足す

## 調査結果

### date-fns のバレルと個別エントリポイント (2026-10-10、vitest 5.0.3、Node 24.21.0、date-fns 4.4.0)

probe は `format` と `ja` だけを import して 1 回 `format` を呼ぶテスト 1 ファイル。`vp test run --project <project> <probe> --experimental.importDurations.print --experimental.importDurations.limit=10 --reporter=default --reporter=<reporter>` で測った。`<reporter>` は `onTestRunEnd` で、テストファイルの `TestModule.diagnostic()` の `collectDuration` (Vitest docs は "The time it takes to import the test module." と書く) を出す。`Duration` の行は phase を合計に対する割合で出し、import の時間を ms で出さない (Vitest docs「Improving Performance」)。差の判定は、比較する回の中央値の差が、両者の最大と最小の差の和を超えるかで行った。指標は `collectDuration` を主にし、内訳の self の和 (`Total import time` の self) を補助にした。Vitest docs は Self を "excluding static imports"、Total を "including static imports" と書く。内訳の total の和は、テストファイルの total が依存の total を含むので入れ子を二重に数え、指標にしない。

測ったマシン (8 コアの macOS) では、ほかの作業が並行して走っていた。比較には、1 分の load average が 7 を下回ってから続けて実行した 5 回ずつを使った。

unit project (Node、pool forks)、5 回ずつ。各回の開始時の 1 分の load average は 5.66 から 6.15:

| probe                                                          | 回  | Total imports | Slowest import (total-time) | Total import time (self / total) | `collectDuration` |
| -------------------------------------------------------------- | --- | ------------- | --------------------------- | -------------------------------- | ----------------- |
| バレル (`date-fns`、`date-fns/locale`)                         | 1   | 5             | 1.08s                       | 1.08s / 2.16s                    | 1082ms            |
| バレル                                                         | 2   | 5             | 1.03s                       | 1.04s / 2.07s                    | 1040ms            |
| バレル                                                         | 3   | 5             | 963ms                       | 965ms / 1.93s                    | 966ms             |
| バレル                                                         | 4   | 5             | 958ms                       | 960ms / 1.92s                    | 961ms             |
| バレル                                                         | 5   | 5             | 954ms                       | 955ms / 1.91s                    | 956ms             |
| 個別エントリポイント (`date-fns/format`、`date-fns/locale/ja`) | 1   | 5             | 55ms                        | 57ms / 110ms                     | 59ms              |
| 個別エントリポイント                                           | 2   | 5             | 44ms                        | 45ms / 88ms                      | 47ms              |
| 個別エントリポイント                                           | 3   | 5             | 44ms                        | 45ms / 88ms                      | 47ms              |
| 個別エントリポイント                                           | 4   | 5             | 43ms                        | 45ms / 87ms                      | 46ms              |
| 個別エントリポイント                                           | 5   | 5             | 43ms                        | 45ms / 87ms                      | 46ms              |

`collectDuration` の中央値は、バレル 966ms、個別エントリポイント 47ms。バレルと個別エントリポイントの差は 919ms で、ばらつき (126ms + 13ms) を超えた。self の和の中央値でも、バレル 965ms と個別エントリポイント 45ms の差 920ms が、ばらつき (125ms + 12ms) を超えた。self の和は 1s 以上を 10ms 単位で表示するので、ばらつきは表示の値で数えた。バレルの 3 回目の内訳では、`date-fns/locale.js` が 500ms、`date-fns/index.js` が 461ms だった。

1 分の load average が 6.82 から 8.84 の間で実行した 10 回ずつでは、バレルの `collectDuration` が 962ms から 2049ms までばらつき、中央値の差 1046ms がばらつき (1087ms + 39ms) を超えなかった。個別エントリポイントはどの回も 86ms 以下で、バレルはどの回も 962ms 以上だった。

browser project (chromium)、5 回ずつ。事前バンドルのキャッシュができたあとに実行した。各回の開始時の 1 分の load average は 5.22 から 7.61。`Import Duration Breakdown` は出なかったので、`collectDuration` だけを指標にした:

| probe                | 1 回目 | 2 回目 | 3 回目 | 4 回目 | 5 回目 | 中央値 |
| -------------------- | ------ | ------ | ------ | ------ | ------ | ------ |
| バレル               | 46ms   | 41ms   | 43ms   | 40ms   | 66ms   | 43ms   |
| 個別エントリポイント | 10ms   | 10ms   | 9ms    | 11ms   | 10ms   | 10ms   |

バレルと個別エントリポイントの差は 33ms で、ばらつき (26ms + 2ms) を超えた。バレルの 5 回目は、実行の間に load average が 5.22 から 7.61 へ上がった。load average が 7.38 から 12.78 の間で実行した 4 回ずつでは、個別エントリポイントが 48ms まで延び、中央値の差 26ms がばらつき (23ms + 37ms) を超えなかった。

キャッシュが無い状態 (worktree を作った直後) での 1 回目の実行は、probe の import をキャッシュに束ねてから走り、Vite は "optimized dependencies changed. reloading" を出さなかった。Vitest の browser mode はテストファイルを事前バンドルの entries に渡し (vitest の v5.0.3 のタグの `packages/browser/src/node/index.ts`)、Vite はキャッシュが無いときに entries からたどった依存を束ねる (Vite docs「Dependency Pre-Bundling」)。キャッシュがある状態で新しい依存を import すると、Vite は束ね直してページを reload する (同)。どちらの状態でも 1 回目は比較から外す。

### override によるオプションの置き換え (2026-09-27、oxlint 1.82.0)

バレルを import する probe を、import 禁止の override の範囲 (`src/lib/`) と範囲外 (`src/test/`) に 1 つずつ置き、`vp lint -f unix` の `no-restricted-imports` の診断を数えた。probe は `date-fns`、`date-fns/format`、`date-fns/locale` を 1 行ずつ import する。

| 設定                       | `src/lib/` の probe                    | `src/test/` の probe |
| -------------------------- | -------------------------------------- | -------------------- |
| 両方に `paths`             | 2 件 (`date-fns` と `date-fns/locale`) | 2 件 (同じ)          |
| 両方から `paths` を消す    | 0 件                                   | 0 件                 |
| トップレベルだけに `paths` | 0 件                                   | 2 件                 |

どの設定でも `date-fns/format` の行は診断されなかった。トップレベルだけに `paths` を置いた設定でも、`scripts/checks/integrity/lint-config.test.ts` は 7 件とも通った。
