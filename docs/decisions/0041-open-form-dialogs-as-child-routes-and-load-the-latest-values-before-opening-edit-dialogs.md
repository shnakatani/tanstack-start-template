# ADR-0041: フォームのダイアログは子 route にし、既存の値を編集するものは loader が最新の値を取り終えてから開く

- Status: Accepted
- Date: 2026-10-12
- 関連: ADR-0010 (分割されない route の property)、ADR-0017 (完了点とブロック範囲)、ADR-0026 (状態の通知)、ADR-0029 (既定の pending 表示)、ADR-0033 (loader と Query)、ADR-0035 (遷移の後の focus と title)、ADR-0040 (View Transitions)

## Context

ページの上に重ねて、入力を保存するフォームのダイアログ (追加、編集) には、開き方に由来する問題が 2 つある。

### 開いたまま mount し続けるダイアログの pending

detached trigger の handle で開くダイアログは、閉じても mount したまま残り、1 つの mutation を持ち続ける。完了点「サーバー応答」(ADR-0017) では、閉じたあとも pending が続く。

| 事実                                                                                                                                                                                                                      | 出典                                                                                                                                                                                                                                                                                                                               |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `onSuccess` が返す再取得の Promise を TanStack Query が待つので、応答のあとも再取得の完了まで `isPending` が続く                                                                                                          | `docs/guides/react/updates.md`「mutation の書き方」の再取得と close                                                                                                                                                                                                                                                                |
| handle の close は、どの保存の `onSuccess` から呼んでも、そのとき開いているダイアログを閉じる。入力フォームは同じ対象で開き直すと別の入力になり、対象の id では開き直したダイアログと見分けられない                       | `docs/guides/react/updates.md`「完了点ごとに Transition を終える」                                                                                                                                                                                                                                                                 |
| TanStack Query は「応答は届いたが `onSuccess` の途中」を公開の状態で持たない。`Mutation.execute` は応答を受けたあと `onSuccess` と `onSettled` を待ってから `success` を dispatch し、その間 `status` は `pending` のまま | [`@tanstack/query-core` 5.104.1 の `Mutation.execute`](https://github.com/TanStack/query/blob/29859ae60c8dca0a5cdbf8abccc775b655cf43e2/packages/query-core/src/mutation.ts#L346-L382)、TanStack/query#9089 の TkDodo の回答 ("If a promise is returned, it will be awaited, and the mutation stays “pending” until that is done.") |

先行する保存の `onSuccess` の close は、閉じて開き直したダイアログを入力ごと閉じうる。確認ダイアログのように開いている対象と mutation の対象を id で比べても、同じ対象で開き直したダイアログは見分けられない。公開の状態からは応答済みかを判定できないので、応答済みかどうかで防ぐこともできない。pending の間は利用者の close を止めれば防げるが、止めると、応答のあと再取得が終わるまでの間に開き直したダイアログも閉じられない。

### 開く前の値の古さ

一覧の行から開く編集ダイアログが、一覧のキャッシュの値をフォームの初期値にすると、別のタブや別の利用者が保存した変更より古い値で編集が始まる。

| 事実                                                                                                                                                                                                                                                                                                                                                                          | 出典                                                                                                           |
| ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| QueryClient のキャッシュはタブごとにあり、保存後の invalidate はそのタブにしか届かない。タブの間でそろえる `broadcastQueryClient` は "broadcasting and syncing the state of your queryClient between browser tabs/windows" のための utility で、"This utility is currently in an experimental stage." とし、"breaking changes will happen in minor AND patch releases" とある | TanStack Query「broadcastQueryClient (Experimental)」                                                          |
| タブへ戻ったときの再取得は、stale な query にだけ走る ("If a user leaves your application and returns and the query data is stale, ...")                                                                                                                                                                                                                                      | TanStack Query「Window Focus Refetching」                                                                      |
| TanStack Form は、`defaultValues` が変わるとフォームの値を差し替える。利用者が触れたフォーム (`isTouched`) は差し替えない。公式のガイドは、データが届く前に作ったフォームへ、届いた値を `defaultValues` として渡す例を示す                                                                                                                                                    | `@tanstack/form-core` 1.33.5 の `FormApi.update` (`shouldUpdateValues`)、TanStack Form「Async Initial Values」 |
| キャッシュに値があると、`useSuspenseQuery` も `useQuery` もまずその値を返して裏で取り直す。前の値を見せないための `isFetchedAfterMount` がある ("This property can be used to not show any previously cached data.")                                                                                                                                                          | TanStack Query「useQuery」の reference                                                                         |
| loader の既定の `staleReloadMode: 'background'` は、stale な match を前の `loaderData` のまま描いて裏で取り直す ("By default, `staleReloadMode` is `'background'`, so stale successful matches keep rendering with their existing `loaderData` while the loader revalidates in the background.")                                                                              | TanStack Router「Data Loading」                                                                                |

前の値でフォームを開いてから新しい値が届くと、上の TanStack Form の挙動により、触れていないフォームは利用者の目の前で値が替わり、打ち始めたフォームは古い値のまま残る。どちらも、開く前に最新の値を取り終えれば起きない。

## Decision

**入力を保存するフォームのダイアログは、開く元のページの route の子 route にする。既存の値を編集するダイアログは、loader を `staleReloadMode: "blocking"` にし、`queryClient.query({ ...options, staleTime: 0 })` を待ってから開く。**

子 route にすると、ダイアログは開くたびに mount し直し、mutation もダイアログごとに別になる。先行する保存の pending は後から開いたダイアログの close を止めず、先行する `onSuccess` の close は自分のダイアログだけを閉じる。URL で共有でき、戻るで閉じる。

### フォームのダイアログ全体

| 対象                   | 決定                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| route                  | 開く元のページを layout route に置き、`<Outlet />` の位置にダイアログの route を描く (TanStack Router の example `location-masking` の形)。URL はマスクしない                                                                                                                                                                                                                                                                                              |
| 開くリンク             | 開く元のページの search を保つ。loader を持たないダイアログのリンクは router の既定の preload (`defaultPreload: "intent"`) のままにする。preload は route の chunk を先に読むだけになる                                                                                                                                                                                                                                                                    |
| 開閉                   | ダイアログは開閉の state を持たず、Dialog の Root に `open` を固定で渡す。閉じる操作 (キャンセル、Escape、外側の押下) と保存の応答の時点で、開く元のページへ新しい履歴で `navigate` し、route ごと unmount する (TanStack Router の example `location-masking` の形)。戻るで開き直せる。比べた案は下の「閉じる時点」                                                                                                                                       |
| close の停止           | 保存の pending の間は、利用者の close (キャンセル、Escape、外側の押下) を止める。応答の前に閉じると route ごと unmount し、保存に失敗したときに入力が残らない。止めるのはそのダイアログ自身の mutation の pending だけ                                                                                                                                                                                                                                     |
| 保存の完了点           | 「サーバー応答」(ADR-0017)。`onSuccess` の先頭で開く元のページへ離れ、再取得を待ってから完了を通知する。閉じると route は unmount するが、`useMutation` に渡した callback はそのあとも走る (`mutate` に渡す callback は "won't run if your component unmounts before the mutation finishes"。TanStack Query「Mutations」)。unmount のあとに走った `onSuccess` では離れない。離れると、保存の途中に戻るで離れて開き直したダイアログを、先行する応答が閉じる |
| 読み込み中             | route の読み込み (loader の取得、component の chunk) が `pendingMs` を超えたら、`pendingComponent` にダイアログの形の読み込み中を出す。無いと router の既定の pending 表示 (ADR-0029) が、開く元のページの `<Outlet />` の位置に出る                                                                                                                                                                                                                       |
| 読み込み開始の読み上げ | 出さない。`pendingMs` の間に本物か読み込み中のダイアログが開き、focus がその中へ移る。ADR-0026 の mutation の開始の通知とは扱いが違う                                                                                                                                                                                                                                                                                                                      |
| 読み込みの失敗         | `errorComponent` もダイアログの形で出す。例外の文言は出さず固定の文言にし、再試行は `router.invalidate()` を呼ぶ                                                                                                                                                                                                                                                                                                                                           |
| 閉じたときの focus     | 下の「閉じたときの focus」の表。`finalFocus` に関数を渡して分ける                                                                                                                                                                                                                                                                                                                                                                                          |
| 遷移の伝え方           | ページとの行き来も、ほかの遷移と同じく伝える。開くとダイアログの title、閉じると開く元のページの title を読み上げる。読み込み中のダイアログを閉じたときは読み上げない。router が確定した location は開く元のページのままで、ページは変わっていない。開いたときは focus を背後のページの見出しへ移さず、Base UI がダイアログの中へ移す (ADR-0035)                                                                                                           |
| View Transition        | 閉じる遷移だけ、Popup を旧画面の snapshot から切り出し、registry の Dialog の閉じ方を当て直す。開く遷移と、別のダイアログに替わる遷移は ADR-0040 のクロスフェードのまま。下の「閉じる遷移の見せ方」                                                                                                                                                                                                                                                        |

### 閉じる時点

閉じる操作の時点で離れ、閉じるアニメーションの後まで待たない。Base UI は閉じたあと、閉じるアニメーションが終わるまで popup を描き続け、終わりを `element.getAnimations()` で見届ける (`@base-ui/react` 1.8.0 の同梱の docs の Base UI「Animation」の "Base UI relies on `element.getAnimations()` to detect if animations have finished on an element."。公開サイトの同じページは "the popup stays rendered in a closing phase until its closing animation finishes" と書く。2026-10-12 に閲覧)。見届けるのは Dialog の部品自身なので、親が部品ごと外すと待てない (推論)。ダイアログの route を離れると、開く元のページの `<Outlet />` は子の match が無くなって何も描かず (`@tanstack/react-router` 1.170.41 の `Match.tsx` のコードの読み)、Root ごと外れる。router 自身は route を離れるときの退場のアニメーションを持たない。maintainer は TanStack/router#2804 で "Router replaces the active Outlet match before transition libraries can retain the previous route element for an exit animation." として TanStack/router#2635 (2026-10-12 時点で open) へまとめ、TanStack/router#1831 で tannerlinsley は "Animations would require simultaneously rendering the states for both the previous and next trees." と書く。route を離れるときに要素へ退場の見せ方を当てる公式の形は、View Transition の名前を要素に付けて `::view-transition-old` にアニメーションを当てる形である (TanStack Router の example `view-transitions`)。

| 案                                                                                                                                                                       | 評価                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 | 採否     |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------- |
| 閉じる操作の時点で離れ、閉じるアニメーションは View Transition の旧画面の snapshot に当て直す (TanStack Router の example `location-masking` と `view-transitions` の形) | 本物、読み込み中、失敗、見つからないのダイアログが同じ閉じ方になる。読み込み中に閉じると、読み込みの結果は router が捨てる。旧画面の Popup は静止画なので、Base UI の閉じるアニメーションそのものは流れず、同じ値の keyframes を当て直す。当て方は下の「閉じる遷移の見せ方」                                                                                                                                                                                                                                                         | **採用** |
| 閉じるアニメーションの後で離れる (`onOpenChangeComplete` で `navigate`)                                                                                                  | 読み込み中のダイアログでは、アニメーションの間に読み込みが終わると本物のダイアログが開き、URL はダイアログのまま残る (下の「実測」)。読み込み中のダイアログだけ待たない例外が要り、閉じ方が 2 つになる。戻る・進むは `onOpenChange` を通らず、閉じるアニメーションを待つ前に URL が変わる。`@base-ui/react` 1.8.0 で `onOpenChange` を呼ぶのは `DialogStore.setOpen` だけで、Base UI は `popstate` を聞かない (コードの読みと、下の「実測」)。この形では、閉じる操作、保存の応答、戻る・進むの 3 つの閉じ方を 1 つの仕組みで扱えない | 却下     |
| Dialog の Root を開く元のページに上げ、Popup の中に `<Outlet />` を置く                                                                                                  | Root が残るので Base UI は閉じるアニメーションを流せるが、`<Outlet />` は子の match が無くなると何も描かないので、中身の無い枠が閉じる見込み (コードの読み、未実測)。example の骨格 (状態ごとに別のダイアログ) から外れる                                                                                                                                                                                                                                                                                                            | 却下     |

### 閉じる遷移の見せ方

ダイアログを閉じる遷移 (閉じる操作、保存の応答、戻る・進む) では、Popup だけを View Transition の名前で旧画面の snapshot から切り出し、`::view-transition-old` に registry の Dialog の閉じ方を当て直す。handle で開く確認ダイアログの閉じ方 (Popup は fade と縮小、Overlay は fade) に近づけるためである。旧画面の snapshot は静止画で、Base UI の閉じるアニメーションは中で流れない (CSS View Transitions Level 1)。

| 対象                                                   | 決定                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| ------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 閉じる遷移の見分け方                                   | ダイアログの route に `staticData: { routeDialog: true }` を書く。ADR-0040 の `defaultViewTransition.types` の関数が UA の判定のあとに、評価時点の `router.state.matches` と行き先の `router.matchRoutes(pathname, search)` で印の付いた match を数え、1 個から 0 個になる遷移にだけ type `route-dialog-close` を足す (`src/lib/route-dialog-view-transition.ts`)                                                                                                 |
| 名前を付ける要素                                       | `useRouteDialog` が返す `popupProps` (`finalFocus` と印の属性 `data-route-dialog`) を Popup に spread する。`data-route-dialog` は route の `staticData.routeDialog` が `true` のときだけ付け、types の関数が数える match と名前を付ける Popup をそろえる。`src/styles.css` が type の付いた遷移の間だけ、`[data-route-dialog]` に `view-transition-name: route-dialog` を付ける。`src/components/ui/dialog.tsx` は変えない                                       |
| 退場                                                   | `::view-transition-old(route-dialog):only-child` に、`ui/dialog.tsx` の Popup の `data-closed:` と同じ `fade-out-0`、`zoom-out-95`、`duration-100` を当て、`fill-mode-both` を足す。fill が無いと、退場の終わりから擬似要素が外れるまでの間に旧画像が元の濃さで戻る                                                                                                                                                                                               |
| Overlay                                                | 名前を付けず、root の snapshot に残す。閉じる遷移の間だけ root の group を 100ms にし、Overlay の `duration-100` にそろえる                                                                                                                                                                                                                                                                                                                                       |
| 別のダイアログに替わる遷移                             | type を返さない。名前が付かないので、新旧の Popup の形を移すアニメーションにならず、ADR-0040 の 250ms のクロスフェードのまま                                                                                                                                                                                                                                                                                                                                      |
| ダイアログの route の子にダイアログの route がある画面 | 今の画面にダイアログの match が 2 個以上あると type を返さない。名前 `route-dialog` は 1 つの capture に 1 つしか置けず、2 つの Popup に付くと遷移が飛ばされる (下の「実測」)。どのダイアログを閉じる遷移も ADR-0040 のクロスフェードのまま。片方の route にだけ印があると、印の付いた match は 1 個なので、印の有るダイアログを閉じる遷移に type を返す。名前は印の有る Popup にだけ付いて退場し、印の無い Popup は root のクロスフェードで消える (下の「実測」) |
| 開く遷移                                               | type を返さない。ADR-0040 のクロスフェードのまま                                                                                                                                                                                                                                                                                                                                                                                                                  |
| reduced motion                                         | 退場は registry の部品の閉じ方と同じアニメーションなので、扱いも registry の部品に従う (ADR-0040 の Consequences)                                                                                                                                                                                                                                                                                                                                                 |

### 閉じたときの focus

Base UI は `finalFocus` を、閉じたときだけでなく、開いたまま unmount したときにも呼ぶ。ダイアログは閉じる操作でも開いたまま route ごと unmount するので、`finalFocus` はどの閉じ方でも unmount の時点で呼ばれる。分けるのは次の 2 つである。

- 開く元のページへ離れた。閉じる操作、保存の応答、戻る・進むのどれでも同じ
- 別のダイアログに替わった。読み込み中のダイアログ (`pendingComponent`) が本物や失敗・見つからないのダイアログ (`errorComponent`、`notFoundComponent`) に替わったとき、開いたまま別の値の URL へ移ったとき (`remountDeps`)、追加と編集のように別のダイアログの URL へ移ったときである

2 つを分ける判定は、ダイアログの route が明示した戻り先 (閉じたときに離れる先。開く元のページ) に、`finalFocus` が呼ばれた時点の router がいるかで行う。いれば離れた、いなければ別のダイアログに替わったとみなす。戻り先はダイアログの route が明示する。TanStack Router の example `location-masking` も、閉じるときは `navigate({ to: photosLayoutRoute.to })` で戻り先を名指す。判定と閉じたときの focus はダイアログの開閉を持つ汎用の hook が持ち、ダイアログの route は戻り先と開いた元の要素の探し方を渡す。route tree の形は読まない。

- 比べるのは pathname で、`router.state.location.pathname` と、戻り先から `router.buildLocation` で組んだ pathname が一致するかを見る。`router.state` は常に最新の値を持つ ("`router.state` is always up to date"。TanStack Router「useRouter hook」)。描画の時点に読んだ値は、unmount の時点の遷移先を映さない
- 戻り先の pathname も呼ばれた時点に組む。`buildLocation` は `params` の関数を呼んだ時点の params で呼ぶ ("it will be called with the current params"。TanStack Router「RouterType」の `.buildLocation`)。戻り先が params を今の値から引き継ぐ形なら、戻った先の params で組むので、別の値の開く元のページへ戻ったときも離れたと判定する
- 戻り先に `from` が無ければ、ダイアログの route の `fullPath` を `from` にして `navigate` と `buildLocation` に渡す。`buildLocation` は `from` が無いと呼んだ時点の path から組むので ("If not provided, the current path will be used."。TanStack Router「RouterType」の `.buildLocation`)、相対の `to` (`..`) は戻るで離れたあとに戻った先から解かれ、戻り先と食い違う。hook はダイアログの route を、部品の木の中の自分の match から得て (`useMatch` を `strict: false` で呼ぶ。TanStack Router「useMatch hook」、`@tanstack/react-router` 1.170.41 のコードの読み)、親の階層は読まない
- router の `caseSensitive` が false (既定。TanStack Router「RouterOptions type」) なら、pathname を大文字小文字を区別せずに比べる。router は `/Items` を `/items` の route に照合し、`router.state.location.pathname` は `/Items` のまま残る (2026-10-12、Vitest の browser mode)。router は大文字小文字を問わず同じ route に照合し、path params の値 (`/groups/G1` と `/groups/g1` の `G1` と `g1`) は区別して取り出すが、pathname 全体を比べるので params の値の違いも区別しなくなる (`@tanstack/router-core` 1.171.34 の `new-process-route-tree.ts` のコードの読み)。戻り先が params を今の値から引き継ぐ形なら、両側が同じ値を持つので結果は変わらない。route ごとの `caseSensitive` は読まない
- 比べる両側の pathname から、末尾の `/` を外す。戻り先は `buildLocation` が router の `trailingSlash` (既定は `never`。TanStack Router「RouterOptions type」) に合わせて末尾の `/` を付け外しして組み、`router.state.location.pathname` は履歴の URL のまま残る。`/items/` を直接開いてからダイアログを開いて戻ると、外さずに比べれば「替わった」と判定する (2026-10-12、Vitest の browser mode)。外すのは `@tanstack/react-router` が export する `trimPathRight` で、router 自身も読み込みの時点の URL を組み直した URL と比べるときに両側へ通す (`@tanstack/react-router` 1.170.41 の `Transitioner.tsx` のコードの読み)
- 戻り先でないページへ離れたときは、替わったときと同じく focus に触れない。開いた元の要素はそのページに無く、route の announcer が見出しへ移す (ADR-0035)

下の表の行は、次の事情で決めた。

- route を離れたとき、開いた元のリンク (行の編集リンク、追加のリンク) へ戻さないと、focus はダイアログと一緒に外れる。利用者は一覧の中の位置を失う。ダイアログの部品は、閉じた理由を問わず unmount したら開いた元の要素へ戻す (`@base-ui/react` 1.8.0 の `FloatingFocusManager` の `returnFocus` の既定、Radix の `FocusScope`、React Aria の `FocusScope` の `restoreFocus`)。戻るで前のページへ戻ったときに前の focus を戻すのは、表示していない document の focus を保つブラウザの振る舞いに倣う。HTML Standard「Focus」は "If a document's fully active state changes, its focused area of the document will stay the same." と書く。bfcache から戻したページの focus の扱いと実測は ADR-0035「bfcache から戻ったときの focus」が持つ
- リンクへ戻した focus は、announcer が動く前に戻り終えるので、見出しへ移らない (2026-10-10 に実測、ADR-0035)
- 開いた元のリンクが無いときは、汎用の hook が見出しへ移す。route の announcer (ADR-0035) にも見出しへ移す働きはあるが、任せない。読み込み中のダイアログから離れると、router が確定した location は開く元のページのままで、announcer はページが変わったと見ず、focus が body に残る (2026-10-12、Vitest の browser mode)
- 替わったときにリンクを返すと、替わる側のダイアログが入力欄へ focus を移すまでの 1 frame だけ、リンクが focus を受ける。消える側の戻し先へ移す処理が microtask で走り、替わる側の初期 focus は次の animation frame で走るからである。消える側の戻し先が替わる側の初期 focus より先に当たる仕組みは floating-ui/floating-ui#3509 (2026-10-10 時点で open) と同じ。`finalFocus` に `false` を返すと focus を動かさない (Base UI「Dialog」の Custom focus management)

### 背後の一覧をそろえる

編集のダイアログは開くたびに最新の値を取るが、背後の一覧はキャッシュの値のまま描かれている。別のタブで保存してから戻り、一覧の `staleTime` の間に開くと、ダイアログは新しい値、背後の行は古い値になる。同じタブの中でダイアログを開いても `visibilitychange` は起きないので、`refetchOnWindowFocus` は動かない (TanStack Query「Migrating to TanStack Query v5」の Window focus refetching no longer listens to the `focus` event)。

| -------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------- |

| 開くたびに一覧を invalidate する                                           | 食い違いが無くても一覧を 1 回取る                                                                                                                                                                                                                                     | 却下     |

`cancelRefetch` は `false` にする。既定の `true` は進行中の取得を捨てて始め直す ("If set to `true`, a currently running request will be cancelled before a new request is made"。TanStack Query「InvalidateOptions」)。進行中の一覧の取得が保存のあとの再取得なら、それは保存を含む一覧を取っているので、捨てると同じ一覧をもう 1 回取ることになる。`false` はその取得を使う。捨てた取得を待っていた側 (保存のあとの再取得を待つ処理) は、新しい取得の Promise に乗り換えるので、先に終わることはない ([`@tanstack/query-core` 5.104.1 の `Query.fetch` の catch](https://github.com/TanStack/query/blob/29859ae60c8dca0a5cdbf8abccc775b655cf43e2/packages/query-core/src/query.ts#L777-L782))。

## Consequences

- 開いた状態は SSR の HTML に入らない。ダイアログは Base UI のポータルの中にあり、hydration の後に開く。フォームは JS が無いと送信できないので受け入れる (2026-10-09、`@base-ui/react` 1.8.0 で実測)
- ダイアログの component は route ごとに別の chunk に分かれ、loader を持たないダイアログの route も chunk を読み終えるまで開かない。開くリンクの preload が hover と focus で chunk を読み始めるので、押す前に読み終えていれば待たない。読み終えていなければ、押してから `pendingMs` までは何も見えない (2026-10-11 に実測)
- `pendingMs` を超えると、component の chunk を読む間もダイアログの形の読み込み中が出る。Automatic Code Splitting の既定のまとめ方は `[['component'], ['errorComponent'], ['notFoundComponent']]` で (TanStack Router「Automatic Code Splitting」の What gets code split?)、`pendingComponent` は route の本体に残り (2026-10-11 に `vp build` の出力で確認)、component の chunk を待たずに描ける (下の「実測」)。pending 表示をページ本体と別のファイルに置く ADR-0010 の決定も、この分割されない挙動を前提にしている
- 保存の応答の前に戻る・進むで route を離れると、close の停止を通らずに unmount する。保存はそのまま続き、失敗すると toast だけが残り、入力は残らない
- 既存の値を編集するダイアログは、開くたびに 1 件を取得し、取り終えるまで開かない
- 開いた後で別のタブや別の利用者が保存すると、開いた時点の値は古くなる。保存は後から保存した側が先の変更を上書きする。この決定は開く時点の古さだけを防ぐ
- 背後の一覧は、開いた項目が食い違ったときだけ取り直す。開かずに一覧だけを見ている間、一覧の古さはタブへ戻ったときの再取得 (`staleTime` を過ぎていれば走る) に任せる。このタブを見たまま別の利用者が保存した変更は、その項目を開くか、タブを離れて戻るまで一覧に出ない
- `cancelRefetch: false` では、別のタブが保存するより前に始まった一覧の取得が進行中だと、invalidate はその取得に吸収される。その取得の結果は保存より古いことがあり、そのときは一覧が古いまま残る
- 既存の値を編集するダイアログは、開く行のリンクが一覧に無いと (戻る・進む、URL を直接開いた)、リンクの `Spinner` が出ないので、`pendingMs` までは何も見えない
- ダイアログの route ごとに、戻り先と開いた元の要素の探し方を渡す。探し方を誤っても、Popup へ `popupProps` を spread し忘れても、型検査も汎用の hook も気付けない。spread し忘れると、閉じたときの focus と閉じる遷移の退場の両方が効かない。閉じたとき、戻るで離れたとき、別のダイアログに替わったときの focus は、そのページの route のテストで確かめることになる
- ダイアログの route には `staticData: { routeDialog: true }` を書く。書き忘れると閉じる遷移の type も Popup の `data-route-dialog` も付かず、ダイアログはクロスフェードで消える。`useRouteDialog` は console に警告し、throw はしない。throw すると、同じ route の `errorComponent` も throw してページごと壊れる
- 閉じる遷移の退場は、`:active-view-transition-type()` に対応するブラウザ (Chrome 125、Safari 18.2、Firefox 147 から。mdn/browser-compat-data の `:active-view-transition-type`、2026-10-12 に確認) でだけ出る。対応しないブラウザでは router が type を渡さず、ADR-0040 のクロスフェードになる。View Transitions に対応しないブラウザでは、ダイアログは即座に消える (コードの読み)
- 戻り先のページの読み込みが `pendingMs` を超えて pending の表示を出すと、表示は View Transition の外で切り替わり、ダイアログは退場を見せずに先に消える見込み (`@tanstack/router-core` 1.171.34 の `load-client.ts` の `offerPending` のコードの読み、未実測)
- ダイアログから戻り先でない別のページへ離れても閉じる遷移の type が付き、ページのクロスフェードが 100ms になる
- ダイアログの route の子にダイアログの route を置き、子の `<Outlet />` を親の Dialog の外に描いて両方を開くと、2 つの Popup の portal がどちらも `aria-hidden` になる (下の「実測」)。Base UI の Dialog は、modal のとき (既定) に、自分の floating tree の外の要素に `aria-hidden` を付ける (`@base-ui/react` 1.8.0 の `FloatingFocusManager` の `markOthers` のコードの読み)。子を親の Popup の中に描く形は測っていない
- 退場の値は `ui/dialog.tsx` の `duration-100`、`data-closed:fade-out-0`、`data-closed:zoom-out-95` を `src/styles.css` に写したもので、registry を取り直しても追随しない。突き合わせの条件は `docs/registry-deviations.md`「registry の値を複製したファイル」が持ち、値がずれると `src/hooks/use-route-dialog.test.tsx` が落ちる

### 再評価の条件

- TanStack/router#2450 が直り、`matchRoute` が `params.parse` した値で照合するようになったら、pending の照合に `params` を渡す (修正は TanStack/router#7776)
