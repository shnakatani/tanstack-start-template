# ADR-0001: ドキュメントは規範・設計ガイド・決定・docstring・履歴の層に分け、ADR は構造・品質特性・戻しにくさに効く選択に限り、参照は規範の側から一方向に張る

- Status: Accepted
- Date: 2026-09-24
- 関連: ADR-0000 (ADR の改訂と置き換えの扱い) / ADR-0002 (rules の 1 項目に書くもの) / ADR-0003 (読み込まれる契機で置き場所を決める)

## Context

`.claude/rules/` は Claude が作業中に読み込む規範を置く場所である。
決定の根拠と改訂履歴を同じ行へ足していくと、規範 1 個に出典と派生規範と履歴が同居した長い項目に育つ。
実装時に必要なのは規範だけだが、取り出すには全文を読むしかない。

ADR も同じように育つ。書き足していくと、決定のほかに、部品をまたいで守る作法の考え方 (なぜその形か) と、その作法で組む手順や落とし穴への対処が混ざる。後者は選択肢から 1 つを選んだ記録ではないので、決定を読む妨げになる。何を ADR にするかを決めずに書くと、この混ざり方は止まらない。

| 出典                       | ADR と、その外に置く文書の分け方                                                                                                                                                                                                                                                                                                                                                           |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Microsoft Well-Architected | ADR に載せるのは "Only include choices that affect the system's structure, key quality attributes, or are difficult to reverse." に限る。"Avoid making decision records design guides." とし、補足は別の文書へリンクして、決定はそれ無しで読めるようにする ("the decision must be clear and stand alone without that material")                                                            |
| arc42                      | §9 Architecture Decisions は "Important, expensive, large scale or risky architecture decisions including rationales." を持つ。§8 Crosscutting Concepts は "practices, patterns, regulations or solution ideas" を持ち、"relate to or influence several of your building blocks" ものを 1 か所に集める。境界は Tip 8-9 の "if (extensive-explanation-required) then concept else decision" |

作法そのものを媒体ごとのファイルが各自で持つと、同じ規範が複数箇所へ写される。
片方だけを直したとき、どちらが現在の規範かを読み手が判断できなくなる。

ソースと設定のコメントも、その形を選んだ理由を出典で示すことがある。このリポジトリはテンプレートとして配布され、利用者は `.claude/rules/` を自分のプロジェクトの規範に合わせて書き換え、差し替える。rules の見出しは編集で変わり、変わっても参照側は静かに宙に浮く。ADR は番号で指し、番号は使い回さない (ADR-0000)。ガイドはテンプレートのコードの組み方を説明する文書で、コードと一緒に書き換わる。rules のように利用者の規範へ差し替える対象ではない。

層の分け方、何を ADR にするか、参照の向きは、どれか 1 つを変えると他の 2 つの前提が崩れる。1 つの決定として持つ。

## Decision

**ドキュメントを規範 (`.claude/rules/`)、設計ガイド (`docs/guides/`)、決定 (`docs/decisions/`)、docstring、履歴 (git) の層に分ける。ADR にするのは構造・主要な品質特性・戻しにくさのいずれかに効く選択に限り、部品をまたぐ作法の説明と手順はガイド、1 つの関数や部品に閉じた注意は docstring に置く。参照は規範の側から張り、ADR とガイドとコードは rules を指さない。**

### 置き場所

| 層         | 置き場所          | 持つもの                                                                                                                                               | 読み手                                |
| ---------- | ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------- |
| 規範       | `.claude/rules/`  | Claude が作業中に読み込む短い規範と理由 1 文。出典として ADR かガイドの節を指す                                                                        | Claude                                |
| 設計ガイド | `docs/guides/`    | 部品をまたいで守る作法の説明 (なぜその形か。作法の選び方で比べた案を含む) と、その作法で組む手順・落とし穴への対処。主題ごとに置き、コードはパスで指す | 人間。rules の出典                    |
| 決定       | `docs/decisions/` | 構造・主要な品質特性・戻しにくさに効く選択と、比較した案、却下の理由、根拠の実測                                                                       | 人間、エージェント (rules の出典から) |
| docstring  | コード            | 1 つの関数や部品に閉じた注意                                                                                                                           | 人間、エージェント                    |
| 履歴       | git               | いつ何を変えたかの記録。ADR の枠内の改訂 (`Revised`) と置き換え (`Superseded`) は ADR 自身にも残す (ADR-0000)                                          | —                                     |

- ADR の中に手順や規範の表が育ったら、ガイドへ出す。ADR には決定と、それを支える比較と観測を残す
- ガイドを読まなくても rules の規範は効く。rules は規範の 1 文と理由を持ち、ガイドは説明と手順を持つ。rules からガイドへどう届けるか (import も言葉での誘導もしない) は ADR-0003 が決める

### 参照の向き

| 参照元                                                   | 指してよい先                                                                                                 |
| -------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| rules                                                    | ADR、ガイドの節                                                                                              |
| ガイド                                                   | ADR、コードのパス、他のガイドの節                                                                            |
| コード (`src/`、`scripts/`、`vite.config.ts` などの設定) | 決定なら `ADR-NNNN`、部品をまたぐ作法ならガイドの節                                                          |
| ADR                                                      | 他の ADR (関連行と本文)、コードのパス、ガイドの節 (補足として。決定はガイドを読まなくても成り立つように書く) |

- ADR とガイドとコードは rules を指さない。rules は利用者が書き換えるので、根拠の側が rules に依存すると参照先が消える。例外は rules の置き場所や書き方を主題にする ADR で、置き場所として rules に触れてよい
- ガイドの節は `docs/guides/<file>.md「<見出し>」` の形で指す。rules からもコードからも ADR からも同じ形で書く
- コメントの理由がそのファイルに閉じるとき (1 つの関数や部品の注意) は、コメント自身に理由を書き、出典を付けない

### 作法の層

ドキュメントの書き方そのものは、下の層が上の層を目的に照らして選別し、この媒体へ再編集して持つ。

| 層         | 置き場所                             | 持つもの                                  |
| ---------- | ------------------------------------ | ----------------------------------------- |
| 原型       | 開発者個人の環境                     | 媒体非依存の原則                          |
| リポジトリ | `.claude/rules/docs.md`              | このリポジトリでの書き方                  |
| 媒体固有   | `.claude/rules/docs.md` の媒体別の節 | その媒体にしかない制約 (rules・AGENTS.md) |

リポジトリ層を置くのは、個人環境の設定が他の開発者の手元では読み込まれないためである。
作業の進め方の規範 (整理の範囲確定、修正の動機の記録) はドキュメントの書き方ではないので、リポジトリ層に持ち込まない。

同じ結論の記述が層をまたいで存在することは許す。
禁じるのは、一方だけを読んだ人が反対の結論に至る状態である。

### 数値の階層

| 媒体         | 数値の扱い                                                                                                                                           |
| ------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| ADR / ガイド | コードで動く数値は書かず、測り方だけ残す。外部の一時点の観測は日付とバージョンを添えて書く。判断の根拠を兼ねる数値は日付を添えて書き、後から消さない |
| rules        | 実測値の詳細を書かない。根拠の実測は ADR かガイドへ                                                                                                  |
| AGENTS.md    | 判断を決める閾値だけを書く                                                                                                                           |

- コードや作業の進行で動く数値 (違反件数、該当箇所数) は、書いた直後から古くなり、古くなっても誰も気付かない。測り方を残せば、読んだ時点の値を読み手が出せる
- 判断の根拠を兼ねる数値を消すと、その判断の論証が成り立たなくなる
- 上流の一時点の観測は、後で上流が変わったときに観測時点が分かるよう、日付と版を添える
- rules と AGENTS.md は作業中に読み込まれる。実測の詳細を置くと規範が埋もれ、AGENTS.md は毎セッション読み込まれるので判断に要る閾値だけを置く (ADR-0002 / ADR-0003)

### 検討した選択肢

#### 作法の説明と手順の置き場所

| 案                                                                  | 評価                                                                                              | 採否     |
| ------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------- | -------- |
| `docs/guides/` に主題ごとに置き、rules は出典としてガイドの節を指す | 人間が主題ごとに読める。rules は規範を自分で持つので、Claude がガイドまで辿らなくても規範は効く   | **採用** |
| ADR に残す                                                          | 決定が説明と手順に埋もれ、決定だけを読めない。Microsoft は ADR を design guide にしないよう求める | 却下     |

rules から import する案、rules を道案内にする案、skill と Storybook の MDX に置く案は、届き方の測定に基づいて ADR-0003 が却下している。

#### ADR にする範囲

| 案                                               | 評価                                                                                                                          | 採否     |
| ------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------- | -------- |
| 構造・主要な品質特性・戻しにくさに効く選択に限る | Microsoft と arc42 §9 が示す範囲と一致する。作法の説明と手順はガイドへ、部品の注意は docstring へ分かれ、ADR は決定だけを持つ | **採用** |
| 迷ったら全部 ADR にする                          | 取りこぼしは無いが、作法の説明・手順・部品の注意が ADR に混ざり、決定を読むには全文を読むことになる                           | 却下     |
| 規模 (変更の行数やファイル数) で決める           | 規模は効き方と対応しない。設定の 1 行でも戻しにくい選択 (依存の待機日数など) は漏れ、手順だけの大きな変更が ADR になる        | 却下     |

#### コメントが指す先

| 案                                          | 評価                                                                                                                        | 採否     |
| ------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- | -------- |
| 決定は ADR を番号で、作法はガイドの節で指す | 利用者が rules を差し替えても参照先が残る。決定が変わっても旧 ADR から置き換え先を辿れる。部品をまたぐ説明は 1 か所に集まる | **採用** |
| ADR だけを指す                              | 作法の手順と説明は ADR ではなくガイドが持つので、作法の理由を指す先が無い                                                   | 却下     |
| rules の見出しで指す                        | 規範の現在の文面に近いが、見出しの編集と利用者の差し替えで行き先が消え、消えても気づけない                                  | 却下     |
| コメントに理由を書き、出典を付けない        | 行き先が消えることは無いが、部品をまたぐ理由を各ファイルに写すことになり、写した箇所ごとに古くなる                          | 却下     |

#### 作法の層

| 案                                 | 評価                                                       | 採否     |
| ---------------------------------- | ---------------------------------------------------------- | -------- |
| 作法をリポジトリ層に再編集して持つ | 他の開発者の手元でも読み込まれ、原型との二重管理にならない | **採用** |
| 作法を原型から写す                 | 個人環境と同時ロードされ、二重管理になる                   | 却下     |
| 作法を個人環境だけに置く           | 他の開発者に届かない                                       | 却下     |

先行例として fallow-rs/fallow の `docs/development/knowledge-architecture.md` がある。"Auto-loaded routers and rules must contain only high-value constraints and routing. Stable explanations belong here so they are read on demand and shared by every host." とし、説明を `docs/` に、Claude 向けの制約を `.claude/rules/` に分けている。ただし fallow は rules に道案内 (routing) も置く。道案内の形は ADR-0003 が読まれないとして却下している。

## Consequences

- 何が ADR に当たるかの線引きは機械で判定できない。レビューで見る。既存の ADR に手順や規範の表が残っていたら、ガイドへ出す
- 原型とリポジトリ層は別リポジトリにあり相互参照を張れない。ドリフトは避けられないが、リポジトリ層が出典を持つのでどちらが古いかは判別できる
- コメントから rules へのリンクを張らないので、コメントを読んだ人が現在の規範の文面を知るには、ADR かガイドを読んだうえで rules を探す
- rules の項目がガイドの節を出典に指しても、Claude がガイドまで辿るかは確かめていない。rules が規範そのものを持つので、辿らなくても規範は効く
- ADR を書き換えたとき、分けたときは、その ADR を出典にする rules、ガイド、コードのコメント、AGENTS.md、README を追随させる。洗い方は `docs/guides/writing-docs.md`「ADR を変えたら参照している側を直す」
- ガイドの見出しを変えたら、`git grep -n 'docs/guides/<file>.md「'` で指している rules・コメント・ADR・他のガイドを直す。見出しへの参照は機械で検査しない。主題の一覧は `docs/guides/README.md` が持つ
- ADR を書き換えるときの扱い (枠内の改訂は `Revised`、決定の置き換えは `Superseded`、実測値の追記や表現の補足は `Revised` に載せない) は ADR-0000 が持つ
