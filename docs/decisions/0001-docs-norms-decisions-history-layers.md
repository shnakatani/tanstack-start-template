# ADR-0001: ドキュメントを規範と経緯と履歴の 3 層に分ける

- Status: Accepted
- Date: 2026-08-17

## Context

`.claude/rules/` は実装時に引く規範を置く場所である。
決定の根拠と改訂履歴を同じ行へ足していくと、規範 1 個に出典と派生規範と履歴が同居した長い項目に育つ。
実装時に必要なのは規範だけだが、取り出すには全文を読むしかない。

rules は frontmatter の `paths:` で条件ロードされる。
`src/**` のような広い glob を持つファイルは、肥大した本文がほぼ毎回 context に載る。

作法そのものを媒体ごとのファイルが各自で持つと、同じ規範が複数箇所へ写される。
片方だけを直したとき、どちらが現在の規範かを読み手が判断できなくなる。

## Decision

### 置き場所

| 置き場所          | 持つもの                       |
| ----------------- | ------------------------------ |
| `.claude/rules/`  | 実装時に引く規範と理由 1 文    |
| `docs/decisions/` | 決定の経緯、選択肢比較、実測値 |
| git 履歴          | いつ何を変えたかの記録         |

### rules の 1 項目に書くもの

- 規範 (何をするか、何を禁じるか)。禁止を書くときは正解を対で書く
- 理由 1 文 (守らないと何が壊れるか)
- 出典キー 1 つ (ADR 番号、仕様の条項番号、上流 issue 番号のいずれか)
- 選択肢に順序があるならその順序 (先に試すもの、最終手段)
- 打ち消し不能または検出不能な落とし穴 (破っても静かに壊れるもの)

実測値の詳細、選択肢の比較と却下理由、改訂履歴、出典の解説文は書かない。ADR が持つ。

### 書くか削るかの判定

1 行ずつ「これを削除したら実装者が誤った選択をするか」を問う。
答えが No なら削る。Yes ならそれは理由ではなく規範なので残す。

1 項目 (箇条書き 1 つ、または表の 1 セル) は 200 字以下にする。
ファイル全体の行数に上限は設けない。
規約があるのに繰り返し破られるなら、ファイルが長すぎて規則が埋もれている兆候として扱い、主題が複数混ざっていれば分割する。

行数を基準にしないのは、Claude Code 公式の Best practices が行数を示さず、1 行ずつの削除可否と「長すぎると規則が埋もれる」症状を基準にしているためである。
表を採ると行数は増えるがトークンはさほど増えない。行数を基準に据えると表を避ける動機が生まれ、引きやすさを損なう。

文字数の測定に `awk` の `length()` を使わない。
macOS 同梱の BSD awk はバイト数を返し、日本語 1 文字を 3 と数える。同じ「200 字以下」が日本語主体の行と ASCII 主体の行で 3 倍ぶれる。
`wc -m` か `perl -CSD` の `length()` を使う。

### 作法の層

ドキュメントの書き方そのものは、下の層が上の層を目的に照らして選別し、この媒体へ再編集して持つ。

| 層         | 置き場所                       | 持つもの                 |
| ---------- | ------------------------------ | ------------------------ |
| 原型       | 開発者個人の環境               | 媒体非依存の原則         |
| リポジトリ | `.claude/rules/doc-hygiene.md` | このリポジトリでの書き方 |
| 媒体固有   | `rules-maintenance.md` ほか    | その媒体にしかない制約   |

リポジトリ層を置くのは、個人環境の設定が他の開発者の手元では読み込まれないためである。
作業の進め方の規範 (整理の範囲確定、修正の動機の記録) はドキュメントの書き方ではないので、リポジトリ層に持ち込まない。

同じ結論の記述が層をまたいで存在することは許す。
禁じるのは、一方だけを読んだ人が反対の結論に至る状態である。

### 数値の階層

| 媒体           | 数値の扱い                                                                 | 規範の置き場所             |
| -------------- | -------------------------------------------------------------------------- | -------------------------- |
| ADR / 解説文書 | コードで動く数値は書かない。外部の一時点の観測と判断の根拠は日付つきで書く | `doc-hygiene.md`           |
| rules          | 実測値の詳細を書かない。根拠の実測は ADR へ                                | `rules-maintenance.md`     |
| AGENTS.md      | 判断を決める閾値だけを書く                                                 | `agents-md-maintenance.md` |

### 検討した選択肢

| 案                       | 評価                                                              | 採否     |
| ------------------------ | ----------------------------------------------------------------- | -------- |
| 規範 + 理由 1 文         | 失敗の記録は残り、詳細は出典キーで辿れる                          | **採用** |
| 規範のみ残す             | 最も短いが、規約を破る場面で理由が 1 クリック先になり形骸化を招く | 却下     |
| 構造だけ変える           | 長い行を分割して表を入れる。引きやすさは改善するが二重管理が残る  | 却下     |
| 作法を原型から写す       | 個人環境と同時ロードされ、二重管理になる                          | 却下     |
| 作法を個人環境だけに置く | 他の開発者に届かない                                              | 却下     |

## Consequences

- rules から根拠を削るぶん、規約の理由を知るには ADR を開く手間が増える。理由 1 文を残すことで日常の判断はカバーする
- 基準は機械強制できない。レビューで見る
- 原型とリポジトリ層は別リポジトリにあり相互参照を張れない。ドリフトは避けられないが、リポジトリ層が出典を持つのでどちらが古いかは判別できる
- ADR は決定と規範が変わったときだけ改訂する。実測値の追記や表現の補足は改訂として扱わない
