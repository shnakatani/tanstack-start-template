# Architecture Decision Records (ADR)

ツールチェーン・lint 方針・型の作り方・UI 基盤など、後から「なぜこうしたのか」を問われる構造的判断を記録する。
何を ADR にするかと、部品をまたぐ作法の説明と手順を `docs/guides/` の設計ガイドへ置くことは ADR-0001 が決める。
**インフラ・ツールチェーン等の構造変更に着手する前に必ず参照する。**

## 新しい ADR を書く手順

Status と決定が変わったときの扱いは ADR-0000 が決める。節の立て方と本文の書き方は `docs/guides/writing-docs.md`「ADR を書く」にある。

1. 連番でファイルを作る: `NNNN-<タイトルの英訳を小文字と dash にしたもの>.md`
2. 見出しとメタデータを次の形で書く。タイトル prefix は `ADR-NNNN:`（ハイフン）で統一する

   ```markdown
   # ADR-NNNN: 日本語タイトル

   - Status: Proposed | Accepted | Deprecated | Superseded
   - Date: YYYY-MM-DD
   - （任意）Revised: YYYY-MM-DD (改訂内容の要約)
   - （任意）Supersedes: ADR-NNNN / Superseded-by: ADR-NNNN
   - （任意）関連: ADR-NNNN (関係の一言)
   ```

3. Context / Decision / Consequences の節を書く
4. この README の一覧の、決定が属するテーマの節へ 1 行追記する
5. 既存の決定を置き換えたときは、旧 ADR の本文と一覧の行の Status を `Superseded` にし、`Supersedes` / `Superseded-by` を対で書く

一覧への追記漏れ、一覧のリンク切れ、`Superseded` の書き漏れと `Supersedes` / `Superseded-by` の対の欠けは `scripts/checks/integrity/adr-index.test.ts` が検出する。本文の `ADR-NNNN` の行き先は見ない。
